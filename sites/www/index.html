BRC-222 JSON-LD Schema

Schema URL: https://brc222.org/schema

This document defines the JSON-LD schema for BRC-222 bridges, a decentralized format for linking digital content across platforms and blockchains with semantic relationships.

BRC-222 defines two kinds of bridge:

  • Content bridges (OrdinalBridge) link a passage or region in one piece of content to another, with a typed relationship.
  • Crosswalk bridges (CrosswalkBridge) link a node in one knowledge graph to the matching node in another, so the two graphs can be traversed as one map. See Crosswalk Bridges.

Version 2.0.0 (2026-10-07). Relationships come in inverse pairs, and direction is gone. See the changelog.

@context

"@context": "https://brc222.org/schema"

Defines the schema namespace for BRC-222 compliant objects. Machine-readable context: /schema.json.

Root Object

{
  "@type": "OrdinalBridge",
  "@id": "bitcoin:inscription:[inscriptionId]",
  "from": { ... },
  "to": { ... },
  "relationship": "cites",
  "explanation": "...",
  "validation": [ ... ]
}

Fields:

  • @type (string): Fixed value "OrdinalBridge"
  • @id (string): Unique identifier. For an inscribed bridge this is the inscription (e.g., bitcoin:inscription:abc123), assigned at the time of inscription. Inscription is optional; a bridge that is not inscribed uses any stable IRI, such as its registry URL.
  • from (object): Describes the source artifact
  • to (object): Describes the target artifact
  • relationship (string): Semantic link type, one of the names in the relationship table, either form of a pair. Expands to an IRI, using CiTO where its meaning matches.
  • explanation (string): Human-readable explanation
  • validation (array): List of third-party attestations

Relationship Types

Every relationship comes as an inverse pair, or is symmetric (its own inverse, because it reads the same from either end). "A isSupportedBy B" and "B supports A" are the same bridge, written from opposite ends, so a bridge can be constructed from either end. There is no direction field. A bridge is stored and published in its canonical form, the first column, with the claim (or the thing being described) as from; an input in the inverse form is turned around. Each page then shows the bridge in its own voice: "supported by B" on the claim, "supports A" on the evidence.

Every relationship can be judged from the two anchored passages and their dates alone; that is what verifiers attest to. The relationships escalate: supports gives evidence for, corroborates adds that the evidence is independent; contradicts says two passages conflict without saying who is right, refutes says one is false, with evidence.

from / to Object Structure

{
  "@type": "WebPage" | "Video" | "Image" | "Audio" | "DigitalArtifact" | "Inscription" | "Sat" | "Claim",
  "@id": "https://example.com" | "bitcoin:inscription:xyz",
  "blockchain": "bitcoin" | "ethereum" | "polygon" | "dogecoin",
  "content": {
    "@type": "TextQuoteSelector",
    "exact": "The quoted content",
    "prefix": "text before",
    "suffix": "text after"
  },
  "metadata": {
    "title": "Optional title",
    "author": "Author or creator",
    "datePublished": "ISO 8601 date"
  }
}

Notes:

  • @type defines content type
  • @id is the unique URL or blockchain reference
  • blockchain identifies the chain the content resides on
  • content supports sub-targeting within a resource
  • metadata provides optional contextual descriptors

TextQuoteSelector

{
  "@type": "TextQuoteSelector",
  "exact": "Selected text",
  "prefix": "Before text",
  "suffix": "After text"
}

Supports precise text selection and resilience to minor text changes.

Validation Entry

{
  "@type": "ValidationEntry",
  "validator": "https://organization.org/profile.json",
  "timestamp": "2025-05-25T12:34:56Z",
  "signature": "..."
}

Signed attestations from verifiers. Verification covers two things: that each end (each context anchor) points to the content it claims, and that the relationship holds. Each entry records who verified the bridge and when. Entries are optional; a bridge with none is unverified.

Crosswalk Bridges

A crosswalk bridge links a node in one knowledge graph to the matching node in another, for example a Wikidata item and the matching record in a library or scientific database. Crosswalks connect entities rather than passages, so their ends are KnowledgeGraphNode objects and their link is a match rather than a relationship.

{
  "@context": "https://brc222.org/schema",
  "@type": "CrosswalkBridge",
  "@id": "bitcoin:inscription:[inscriptionId]",
  "from": {
    "@type": "KnowledgeGraphNode",
    "@id": "http://www.wikidata.org/entity/Q1035",
    "graph": "https://www.wikidata.org/",
    "identifier": "Q1035",
    "label": "Charles Darwin"
  },
  "to": {
    "@type": "KnowledgeGraphNode",
    "@id": "http://id.loc.gov/authorities/names/n78095637",
    "graph": "https://id.loc.gov/authorities/names/",
    "identifier": "n78095637",
    "label": "Darwin, Charles, 1809-1882"
  },
  "match": "exactMatch",
  "explanation": "Both nodes describe the naturalist Charles Darwin (1809-1882).",
  "validation": [ ... ]
}

Fields:

  • @type (string): Fixed value "CrosswalkBridge"
  • @id, explanation, validation: As for OrdinalBridge.
  • from / to (object): A KnowledgeGraphNode in each graph.
  • match (string, required): How closely the two nodes correspond, read as "from match to". Values: exactMatch, closeMatch, broadMatch (from is broader than to), narrowMatch (from is narrower than to), relatedMatch. These map to the SKOS mapping properties of the same names, so a crosswalk can be read as a SKOS mapping. There is no default: the strength of the match is part of what verifiers attest to.
  • Crosswalk matches follow the same principle as relationship pairs: swap the ends and a broadMatch becomes a narrowMatch, while exact, close and related matches read the same either way.

KnowledgeGraphNode

{
  "@type": "KnowledgeGraphNode",
  "@id": "https://graph.example.org/entity/123",
  "graph": "https://graph.example.org/",
  "identifier": "123",
  "label": "Human-readable name"
}
  • @id (string, required): The node's dereferenceable IRI in its own graph.
  • graph (string, required): IRI identifying the knowledge graph, dataset or authority file the node belongs to.
  • identifier (string, optional): The node's local identifier within that graph (e.g., a Wikidata Q-number).
  • label (string, optional): A human-readable name, so the crosswalk can be checked without dereferencing either IRI.

Verification of a crosswalk checks that each @id resolves to a node in the stated graph and that the match holds.

Changelog

  • 2.0.0 (2026-10-07): relationships come in inverse pairs (isSupportedBy and supports are one bridge), or are symmetric (contradicts: contradiction is mutual, so it has no passive form); direction removed; contextualizes replaced by qualifies / isQualifiedBy; corroborates gains an inverse; is-member-of becomes isMemberOf; relationship expands to an IRI (CiTO where it matches); the vocabulary is published at /vocabulary.json. Breaking.
  • 1.3.0 (2026-10-07): removed amplifies; whether one text gave another more reach cannot be judged from the passages themselves.
  • 1.2.0 (2026-10-06): added extends.
  • 1.1.1 (2026-10-06): crosswalk match required; crosswalks carry no direction.
  • 1.1.0 (2026-10-05): added corroborates, is-member-of and crosswalk bridges.
